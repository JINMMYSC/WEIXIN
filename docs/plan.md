# 微信输入法 3.5.3 离线键盘重建计划

状态：已获用户批准执行。基础工程、无签名 CI、资源格式初勘和可测试的输入/候选闭环已建立；原版算法、完整资源接入、动态调用链和签名安装仍未完成。以下阶段门槛继续有效。

目标：以用户设备上可运行的微信输入法 3.5.3 为参照，重建离线键盘界面与输入行为。第一条交付链路为全键盘拼音输入、候选展示、选择上屏、删除和修改；再覆盖其他离线输入模式。

架构方向：键盘界面、输入会话、输入引擎、资源装载分别承担独立职责，通过操作事件与结果快照连接。先建立原版行为基准和证据，再实现可测试模块。GitHub Actions 负责构建和自动化测试，用户 iPhone 负责真实键盘体验对照。

技术方向：拟采用 Swift/UIKit 编写主 App 与键盘界面；引擎语言根据逆向规格选择，优先评估 C++ 与 Objective-C++ 桥接是否必要；使用 XCTest 与数据驱动回放测试。尚无重建工程，不虚构已经存在的函数、工程路径或构建命令。

## 3. “一致”的验收定义

只对明确记录的版本、环境、初始状态和测试集承诺验收结果，不宣称覆盖所有可能输入。以下数量和容差为建议值，基准采样结束后由用户确认并锁定；不得因实现困难而自行降低。

| 维度 | 比较内容 | 建议验收方式 |
|---|---|---|
| 输入状态 | 组合串、光标、已提交文本、候选内容及顺序 | 固定用例逐事件比对，要求全部一致；未通过逐条列出 |
| 界面 | 键位、尺寸、间距、颜色、字号、候选区和状态切换 | 同设备截图叠加；建议关键几何偏差不超过 1 pt，动态系统区域预先标记排除 |
| 交互 | 点击、长按删除、候选展开、模式切换、返回键 | 比较状态变化和可见结果；动画时间单列，不以单帧截图代替 |
| 资源 | 词库、模型版本及配置 | 记录哈希和装载参数；不同资源版本的结果不混作同一基准 |
| 学习 | 清洁状态与使用后状态 | 分组测试；不能控制原版状态时标记为受限样本，不能算精确复现 |
| 性能 | 冷启动、候选更新、连续输入、内存压力 | 同设备重复测量；建议每场景至少 30 次，报告中位数与 P95，阈值在基准后冻结 |
| 稳定性 | 快速输入、切换应用、扩展重启、异常资源 | 建议 1,000 次操作回放及 30 分钟实机使用，无崩溃、丢字和重复上屏 |

候选一致率只按事先固定的事件与候选位置计算，说明分母和失败项。截图误差、候选一致率和功能覆盖率分别报告，不合并为“还原百分比”。

## 4. 路线比较

1. **推荐：行为对照与逆向交替推进。** 每分析一个模块，就用原版样本验证并重建；可持续交付，也能及早发现理解错误。
2. 全量逆向后再开发：内部理解可能更完整，但较晚才能发现缺少模型、资源或运行环境，工期难估。
3. 通用输入引擎加相似界面：能较快获得可用键盘，但候选排序和学习行为可能不同，不作为本项目精确对照目标的默认替代方案。

## 6. 数据流与测试位置

```text
原版 iPhone：固定初始状态 → 操作序列 → 每步截图/候选/提交结果
                                         ↓ 基准轨迹
新键盘 UI → 输入事件 → 会话/引擎 ← 资源装载
    ↑                    ↓
    └── 状态快照/候选 ────┤
                         └→ 提交动作 → 测试宿主/真实输入框
                                ↓
                    与基准逐步比较 → 差异清单

CI：模块回放测试 → 模拟器宿主测试 → 构建产物
实机：键盘启用 → 实际输入框交互 → 截图/性能/稳定性对照
```

测试接口与正常调用接口一致，不为测试复制一套输入逻辑。原版完整回放自动化是否可行先验证；不可行时由用户采样，不声称 CI 能远程操作其 iPhone。

| 失败场景 | 对应测试 | 处理目标 |
|---|---|---|
| 候选迟到或顺序错乱 | 快速输入、删改后返回旧候选 | 会话版本隔离，旧结果不覆盖新状态 |
| 上屏后重复提交 | 连续选词、切换键盘返回 | 一次操作对应一次提交 |
| 光标移动后删错文本 | 中间插入/删除、选区替换 | 依据有效上下文同步状态 |
| 资源缺失或截断 | 文件错误注入 | 明确失败并可恢复，不越界读取 |
| 扩展被系统终止 | 切换应用与重启 | 已提交文本不损坏，会话恢复符合规格 |
| 网络关闭 | 飞行模式实测 | 已承诺离线功能不依赖在线响应 |
| 签名或描述文件不匹配 | CI 检查及安装验证 | 构建报错可定位，未安装不算交付 |

## 7. GitHub CI 与实机安装安排

建议两个独立工作流：普通提交运行构建/测试；用户触发签名构建时读取受保护的签名材料。第三方 Action 固定到已核验版本或提交；不从外部拉取未固定的执行脚本。

GitHub 官方流程支持在 macOS runner 中通过 Secrets 导入 Apple 证书和描述文件，并在临时钥匙串中完成签名。证书私钥和密码不写入仓库、日志或普通测试产物。主 App 和扩展各自的签名配置均需核对。[GitHub 官方签名说明](https://docs.github.com/en/actions/how-tos/deploy/deploy-to-third-party-platforms/sign-xcode-applications)

开发安装路径需要匹配的开发证书、App ID 和包含目标设备的描述文件。当前尚未确认用户开发者账号和签名材料；这是签名安装任务的前置条件，不阻塞静态分析与模拟器测试。[Apple 开发描述文件说明](https://developer.apple.com/help/account/provisioning-profiles/create-a-development-provisioning-profile)

具体选择开发/Ad Hoc 安装还是 TestFlight，在确认账号条件后决定并验证。下载 IPA 文件不等于能够直接安装。首个签名任务必须包含“下载—安装—启用键盘—实际输入”完整验证。

## 8. 阶段依赖、估时与暂停条件

P0 与 P1 可按各自授权独立推进；P2 依赖 P1 的装载入口；P3 依赖基准与静态问题清单；P4 的空工程 CI 可提前，但引擎实现依赖 P1—P3；P5/P6 依赖资源和行为规格。

不预先承诺完整复制的固定工期。每一任务启动时给出本轮范围和时间预算；P1 完成后基于函数可读性重新估计，P2/P3 完成后再估计引擎重建。使用完成条件判断进度，而非用花费天数推断完成比例。

暂停相关任务的条件：关键代码无法可靠解释、核心资源无法解析或缺失、原版行为不可重复、需要但不具备内部调试条件、签名安装条件缺失。暂停只影响依赖该条件的任务；向用户提交实际证据与备选路线。
